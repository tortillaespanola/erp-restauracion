# AUDITORIA_ARQUITECTURA_CATALOGO.md

**Tipo:** Auditoría de solo lectura. No se ha modificado ningún archivo de código ni de base de datos para producir este informe.
**Fecha:** 10-09-2026.
**Objetivo:** Servir de base a un contrato de refactor sobre el catálogo de ítems (ingredientes, artículos de compra, semielaborados, productos finales), producción, categorías/unidades de medida, i18n y el estado "Servido" de pedidos.

---

## 0. Aviso importante sobre el origen del esquema

El repositorio **no tiene un `schema.sql` consolidado ni un dump de tipos generado** (`database.types.ts` no existe). Todo el esquema se reconstruye a partir de `supabase/migrations/*.sql` (71 archivos, el más antiguo fechado `20260731`).

Ese primer archivo ya referencia tablas totalmente formadas (`semielaborados`, `productos_finales`, `producciones_semielaborado`, `producciones_producto_final`, `ingredientes`, `receta_producto_final`, `receta_semielaborado`, `entrada_material`, `articulos_compra`, `albaranes_compra`, `proveedores`, `clientes`...) que **nunca se crean con `CREATE TABLE` en ningún archivo de este repo**. `20260807_negocio_id_particion.sql` lo confirma explícitamente: hace `ALTER TABLE` sobre 32 tablas preexistentes para añadirles `negocio_id`, y su comentario de cabecera dice que es el primer trabajo de particionado por negocio que se hace.

**Consecuencia práctica:** para `semielaborados`, `productos_finales`, `producciones_semielaborado`, `producciones_producto_final`, `articulos_compra`, `proveedores`, `clientes`, `receta_producto_final`, `receta_semielaborado`, `entrada_material`, `albaranes_compra/venta`, etc., **el esquema base (columnas originales, PK, tipo de `id`) se creó fuera de este repo** (Supabase Studio o SQL suelto no versionado). Lo que sigue reconstruye con certeza total solo lo que se ve en las migraciones (columnas añadidas/alteradas después, triggers, FKs); las columnas base se marcan **"inferida, no verificada"** cuando solo se deducen de su uso en funciones/triggers, nunca de un `CREATE`/`ALTER` explícito.

Cinco tablas sí se crean íntegramente dentro del set de migraciones y están reconstruidas con confianza total: `ingredientes`, `categorias_articulo`, `tandas_produccion`, `previsiones_distribucion_pf`, `unidades_medida`.

**Segunda anomalía a tener en cuenta:** `20260907_reescribir_42_policies_negocio_actual.sql` y `20260907_default_negocio_id_dinamico.sql` iteran sobre un array fijo de "42 tablas" que incluye `previsiones_distribucion_pf` y `unidades_medida` — pero esas dos tablas no existen hasta `20260912` y `20260923` respectivamente (fechas posteriores). El orden cronológico por nombre de archivo **no es fiable como orden de replay** en este repo — como mínimo esos dos archivos `20260907_*` fueron reescritos después de su aplicación original. Un `supabase db reset` que reproduzca los archivos en orden de nombre fallaría hoy en esos dos ficheros. No afecta a las conclusiones de estado final, pero es relevante si el refactor toca el pipeline de migraciones.

## 1. Schema de tablas de ítems y producción

### 1.1 `ingredientes` (creada íntegramente en `20260813_ingredientes.sql`)

```sql
create table ingredientes (
  id bigint generated by default as identity primary key,
  nombre text not null,
  unidad text not null,                 -- legacy texto libre; unidad_id es ahora la fuente de verdad
  negocio_id uuid not null default negocio_actual() references negocios(id),
  created_at timestamptz not null default now(),
  categoria_id bigint not null references categorias_articulo(id),   -- añadida 20260814
  unidad_id bigint not null references unidades_medida(id)           -- añadida 20260923
);
```
RLS: policy única `"Acceso total temporal"` (`negocio_id = negocio_actual()`); grants `select, insert, update, delete` a `authenticated`.

**Triggers:**
- `trg_sincronizar_unidad_texto_ingredientes` (before insert/update de `unidad_id`) → `sincronizar_unidad_texto()`: copia `unidades_medida.codigo` a la columna legacy `unidad` cada vez que cambia `unidad_id`.
- `trg_validar_cambio_unidad_ingredientes` (before update de `unidad_id`) → `validar_cambio_unidad_vinculado()`: bloquea el cambio si el ingrediente está vinculado (vía `articulo_ingrediente`) a un artículo con `unidad_id` distinto.

**FKs que apuntan a `ingredientes.id`:**
- `articulo_ingrediente.ingrediente_id → ingredientes(id) on delete cascade`.
- `receta_producto_final.ingrediente_id → ingredientes(id)` (nullable; CHECK `solo_un_tipo_ingrediente_pf` exige exactamente uno entre `articulo_id` / `ingrediente_semielaborado_id` / `ingrediente_id`).
- `receta_semielaborado.ingrediente_id → ingredientes(id)` (mismo patrón, CHECK `solo_un_tipo_ingrediente`).

Sin columna de caducidad.

### 1.2 `articulos` no existe — es `articulos_compra`

No hay ninguna tabla llamada literalmente `articulos`. El catálogo de compra vive en **`articulos_compra`** (tabla base no versionada). Columnas confirmadas por migraciones:
- `negocio_id uuid not null default negocio_actual() references negocios(id)`.
- `categoria_id bigint not null references categorias_articulo(id)` (`20260814`; la columna `categoria` de texto libre se **eliminó**: `alter table articulos_compra drop column categoria`).
- `unidad_id bigint not null references unidades_medida(id)` (`20260923`); columna legacy `unidad text` se mantiene sincronizada por `trg_sincronizar_unidad_texto_articulos`.
- `codigo` (preexistente, usado por `generar_codigo()`/`secuencias_lote`).

Referenciada por: `lineas_pedido_compra.articulo_id not null`, `lineas_pedido_venta.articulo_id`, `lineas_albaran_venta.articulo_id`, `receta_producto_final.articulo_id`, `receta_semielaborado.articulo_id` — todas `→ articulos_compra(id)`.

**Triggers:** `trg_sincronizar_unidad_texto_articulos`, `trg_validar_cambio_unidad_articulos` (mismos patrones que en ingredientes).

### 1.3 `semielaborados` (base no versionada; columnas añadidas confirmadas)

- `negocio_id uuid not null default negocio_actual() references negocios(id)`.
- `dias_caducidad_default integer` — **nullable**, sin default (`20260824_fecha_caducidad_semielaborado.sql`).
- `unidad_id bigint not null references unidades_medida(id)` (`20260926`, backfilleada desde `unidad` texto); legacy `unidad` sincronizada por `trg_sincronizar_unidad_texto_semielaborados`.
- **Sin `categoria_id`** — la categorización con `categorias_articulo` solo se aplicó a `articulos_compra` e `ingredientes`, nunca a `semielaborados`.

**Triggers:** solo `trg_sincronizar_unidad_texto_semielaborados`. El cálculo de caducidad vive en `producciones_semielaborado`, no aquí.

**FKs que apuntan a `semielaborados.id`:** `producciones_semielaborado.semielaborado_id` (inferida), `receta_semielaborado.semielaborado_id`/`.ingrediente_semielaborado_id` (auto-referencia, inferidas), `receta_producto_final.ingrediente_semielaborado_id` (inferida).

### 1.4 `productos_finales` (base no versionada; columnas añadidas confirmadas)

- `negocio_id uuid not null default negocio_actual() references negocios(id)`.
- `dias_caducidad_default integer` — **nullable**, sin default (`20260803_producto_final_caducidad_merma.sql`).
- `unidad_id bigint not null references unidades_medida(id) default <id de 'ud'>` (`20260926`) — documentado explícitamente como **el primer concepto de unidad que ha tenido esta tabla**: *"productos_finales NUNCA tuvo columna `unidad` (ni texto ni ningún otro campo)"*. Todas las filas existentes se backfillearon a `'ud'`. **No existe columna legacy `unidad` texto aquí** (a diferencia de ingredientes/articulos_compra/semielaborados) y por tanto tampoco trigger de sincronización.

**Sin triggers propios** (los de caducidad/unidad viven en `producciones_producto_final`, `ingredientes`, `articulos_compra`, `semielaborados`, `articulo_ingrediente`).

**FKs que apuntan a `productos_finales.id`:** `producciones_producto_final.producto_final_id` (inferida), `lineas_pedido_venta.producto_final_id` (nullable, CHECK `chk_lineas_pedido_un_origen`), `lineas_albaran_venta.producto_final_id` (nullable desde `20260801`, CHECK `chk_lineas_albaran_venta_origen`), `receta_producto_final.producto_final_id` (inferida), `previsiones_distribucion_pf.producto_final_id not null`.

## 2. Campo caducidad / `dias_caducidad_default`

| tabla.columna | nullable | default | añadida por |
|---|---|---|---|
| `productos_finales.dias_caducidad_default` | sí | ninguno | `20260803_producto_final_caducidad_merma.sql` |
| `producciones_producto_final.fecha_caducidad` | sí | ninguno, calculada por trigger al cerrar | `20260803` |
| `semielaborados.dias_caducidad_default` | sí | ninguno | `20260824_fecha_caducidad_semielaborado.sql` |
| `producciones_semielaborado.fecha_caducidad` | sí | ninguno, calculada por trigger al cerrar | `20260824` |
| `entrada_material.fecha_caducidad` | preexistente, no creada en ninguna migración leída | desconocido | esquema base |

**No existe ninguna columna llamada literalmente `caducidad`.** El patrón es siempre `dias_caducidad_default` (integer, en la tabla de catálogo/tipo) + `fecha_caducidad` (date, en la tabla de lote de producción), calculada una sola vez por un trigger `before update` en la transición `'abierta'→'cerrada'`, y editable después manualmente vía `rpc_editar_produccion_semielaborado`/`rpc_editar_produccion_producto_final` (ambas ganaron un parámetro `p_fecha_caducidad date default null` en `20260824b_rpc_editar_produccion_fecha_caducidad.sql`).

**Componentes frontend que leen/escriben caducidad** (grep sobre `pages/`+`components/`): `AlbaranesCompra.jsx`, `Producciones.jsx`, `ProduccionProductosFinales.jsx`, `ProductosFinales.jsx`, `Semielaborados.jsx`, `AjusteStockForm.jsx`, `AlbaranCompraForm.jsx`, `AlbaranVentaForm.jsx`.

## 3. Categorías y unidades de medida: tabla configurable, no hardcodeadas

Ambas viven en **tablas propias con FK**, no en un enum/array de código — pero con matices importantes de cara al refactor:

### `unidades_medida` (creada `20260923_unidades_medida.sql`)
```sql
create table unidades_medida (
  id bigint generated always as identity primary key,
  codigo text not null,
  nombre text not null,
  tipo text not null check (tipo in ('peso', 'volumen', 'unidad')),
  negocio_id uuid not null default negocio_actual() references negocios(id),
  created_at timestamptz default now()
);
-- unique global inicial → unique (negocio_id, codigo) tras 20260907 (por negocio)
```
Seed: `('kg','Kilogramo','peso')`, `('l','Litro','volumen')`, `('ud','Unidad','unidad')`. Grants: **solo `select, insert, update`** — sin `delete` para `authenticated` (a diferencia de todas las demás tablas de catálogo del proyecto, que sí tienen los 4). Puede ser intencional o un descuido; conviene confirmarlo antes de asumir que las unidades no se pueden borrar vía API.

`ingredientes`, `articulos_compra` y `semielaborados` mantienen su columna legacy de texto libre `unidad` **sincronizada automáticamente** por trigger desde `unidad_id` — el propio migration documenta que esto es deuda técnica deliberada: *"80 ocurrencias de `.unidad` repartidas en 12 archivos del frontend [...] dropearla ahora rompería la app en producción antes de que cada pantalla se migre"*. `productos_finales` es la excepción: nunca tuvo columna de texto, se le añadió `unidad_id` directamente con default fijo a `'ud'`, y **el propio migration decidió explícitamente no ofrecer selector de otra unidad en el alta**, citando que "8+ sitios" del frontend ya asumen que un producto final se cuenta en unidades.

**No hay pantalla de administración de `unidades_medida` ni de `categorias_articulo`** — `Configuracion.jsx` (única pantalla de ajustes) solo gestiona `empresa_config` (datos fiscales/logo). Ambas tablas son configurables en base de datos pero no editables desde ninguna UI hoy.

### `categorias_articulo` (creada `20260814_categorias_articulo.sql`, ampliada `20260901`)
```sql
create table categorias_articulo (
  id bigint generated by default as identity primary key,
  nombre text not null,
  acronimo text not null,
  negocio_id uuid not null default negocio_actual() references negocios(id),
  created_at timestamptz not null default now()
);
```
Sin UNIQUE en `nombre`/`acronimo` — nada impide duplicados a nivel de base de datos, solo la convención. Seed actual: Verduras/VEG, Lácteos y Ovoproductos/LYO, Condimentos y Básicos/COC, Packaging/PKG, Carnes/CAR, Pescados y Mariscos/PYM, Cereales-Legumbres-Pan y Pasta/CLP. Referenciada por `articulos_compra.categoria_id` e `ingredientes.categoria_id` (ambas NOT NULL). **`semielaborados` y `productos_finales` no tienen categoría** — el concepto nunca se extendió a esas dos tablas.

## 4. Estado de pedido "Servido": texto plano, sin ENUM ni CHECK

- **`pedidos_venta.estado`**: `text not null default 'pendiente'` (`20260801_pedidos_venta.sql`), con el comentario `-- pendiente | en_produccion | servido | cancelado`. **Nunca se añadió un CHECK** que restrinja los valores — el vocabulario de 4 valores es solo un comentario SQL, no algo que la base de datos imponga. Los valores literales en minúscula español (`'servido'` incluido) los escriben exclusivamente los triggers `actualizar_estado_pedido_por_produccion()` y `actualizar_estado_pedido_por_servicio()`.
- **`pedidos_compra.estado`**: mismo patrón — `text not null default 'pendiente'`, comentario `-- pendiente | recibido | cancelado`, sin CHECK.
- `20260928_grupo_estado_pedidos_venta.sql` añade una columna **derivada** (no un cambio de tipo):
  ```sql
  alter table pedidos_venta add column grupo_estado smallint generated always as (
    case when estado in ('servido', 'cancelado') then 1 else 0 end
  ) stored;
  ```
  Solo para ordenar en servidor (activos vs. cerrados); no valida ni restringe `estado`.
- **No existe ningún `CREATE TYPE ... AS ENUM` en todo el esquema** (grep completo sin resultados). Otros campos "estado" del proyecto sí tienen CHECK inline (`tandas_produccion.estado check (estado in ('abierta','cerrada'))`, `incidencias_reparto_pedido.estado check (... in ('pendiente','regularizado','ignorado'))`), pero los dos campos de estado de pedido (venta y compra) no.

**Componente/columna:** `pedidos_venta.estado` (texto plano) — leído/escrito en `frontend/src/pages/Pedidos.jsx` (constante `ESTADOS_PEDIDO = ['pendiente', 'en_produccion', 'servido', 'cancelado']`, línea 35) y `frontend/src/pages/PedidosDelDia.jsx`. La traducción a etiqueta visible se resuelve en la UI con `t('enums:estado_pedido.<clave>')` — el valor crudo guardado en base de datos sigue siendo la palabra en español (`servido`), no un código numérico ni un id de tabla de lookup.

**Implicación para el refactor:** hoy nada impide a nivel de base de datos que un `UPDATE` manual o una migración futura escriba un valor arbitrario en `estado`; el contrato de valores válidos vive únicamente en el código de los triggers y del frontend.

## 5. Sistema de i18n: ya implantado, con 4 excepciones detectadas

Existe un sistema real de `i18next` con namespaces por archivo, 3 locales completos (`es`, `en`, `de`) bajo `frontend/src/i18n/{es,en,de}/*.json` (29 archivos de traducción por locale, un namespace por pantalla/formulario/dominio: `common`, `enums`, `estados_calculados`, `pedidos`, `pedidos_compra`, `ingredientes`, `producciones`, etc.).

**Adopción:** de 33 archivos en `pages/` + `components/` (21 + 12), **29 usan `useTranslation`** (87.9%). Los 4 que NO lo usan:
- `pages/CierreTanda.jsx` — pantalla completa (378 líneas) 100% en español hardcodeado: título `"Cierre / entrega"`, subtítulo `"Reparte lo producido en esta tanda entre los pedidos que la componen..."`, mensajes de `alert()` como `"Error al crear un albarán del reparto — el resto puede haber quedado a medias..."`.
- `components/AlbaranVentaForm.jsx` (701 líneas) — ejemplos: `alert('Selecciona un lote e introduce una cantidad válida')`, `alert('Añade al menos una línea de producto')`, texto `"Este albarán se enlazará a las líneas pendientes del pedido seleccionado."`.
- `components/FacturaVentaForm.jsx` (181 líneas) — no auditado línea a línea, pero sin ningún `useTranslation`.
- `components/AuthGate.jsx` (77 líneas) — pantalla de login/guard, probablemente strings mínimos pero también sin i18n.
- (`components/ui.jsx` tampoco usa `useTranslation`, pero es la librería de componentes base de UI — sus props de texto las pasa siempre el llamador, no contiene strings propios de dominio; no cuenta como una pantalla sin traducir).

## 7. Cierre de producción: ¿fuerza peso, o ya admite otras unidades?

**Aclaración de premisa:** `CierreTanda.jsx` no es la pantalla donde se "cierra" una producción — es la pantalla de **reparto** posterior (genera los albaranes de venta repartiendo lo ya producido y cerrado entre los pedidos de la tanda). No contiene ningún literal `"peso"` ni `"neto"`; sus cantidades (`p.cantidadPedida.toFixed(3)`, `g.disponibleTotal.toFixed(3)`) son genéricas, sin unidad explícita en el string (el operador ve solo el número).

El cierre real de una tanda de producción ocurre en:
- **`Producciones.jsx`** (producción de **semielaborados**): el input de cantidad producida usa `produccion.semielaborados?.unidad` (columna dinámica, ya parametrizada vía `unidad_id → unidades_medida`, línea ~1086/1510). **Ya es agnóstico a la unidad** — kg, litro o unidad, lo que tenga configurado ese semielaborado.
- **`ProduccionProductosFinales.jsx`** (producción de **productos finales**): el input usa una constante local `UNIDADES = t('produccion_productos_finales:unidad_larga')`, que en las 3 traducciones resuelve siempre a **"unidades"/"units"/"Einheiten"** (`unidad_larga`/`unidad_corta` en `i18n/es/produccion_productos_finales.json`, valores fijos `"unidades"`/`"uds."`). No lee `productos_finales.unidad_id` en ningún punto de este archivo (aunque la columna existe en base de datos desde `20260926`, con default `'ud'`).

**Respuesta concreta:** no hay ningún forzado a "peso neto final" en ningún sitio de este flujo — pero **`productos_finales` sí está efectivamente bloqueado a la unidad "ud" (unidades de conteo)** de forma consistente en frontend y backend: la migración `20260926_unidad_semielaborados_productos_finales.sql` documenta la decisión explícita de no ofrecer selector de otra unidad al alta de un producto final, y `ProduccionProductosFinales.jsx` usa una etiqueta i18n fija ("unidades") en vez de leer `unidad_id` dinámicamente como sí hace `Producciones.jsx` con los semielaborados. Es decir: el subsistema de semielaborados ya es unit-agnostic de punta a punta; el de productos finales tiene la columna preparada en base de datos pero la UI todavía no la usa — es la pieza concreta que un refactor "productos finales por peso" tendría que tocar.

## 8. Resumen de puntos de fricción para el contrato de refactor

1. Esquema base de las tablas de catálogo/producción no está versionado — cualquier cambio DDL sobre ellas debe partir del estado real de la BD (pedir `\d+ <tabla>` o export de Supabase), no asumir columnas por las migraciones.
2. `productos_finales` y `semielaborados` no comparten estructura de "unidad" en la UI aunque sí en BD (`unidad_id` en ambas) — inconsistencia real, no solo de nombres.
3. `productos_finales`/`semielaborados` no tienen `categoria_id` — si el refactor quiere categorías uniformes en todo el catálogo, es una ampliación nueva, no un bug.
4. `unidades_medida` no tiene grant de `delete` ni pantalla de administración — a confirmar si es deliberado.
5. `pedidos_venta.estado`/`pedidos_compra.estado` no tienen CHECK — cualquier normalización a un tipo controlado (ENUM, tabla lookup) requerirá añadir la restricción que hoy no existe, con el riesgo de que datos históricos ya la violen.
6. i18n cubre el 88% de pantallas/componentes; `CierreTanda.jsx` y `AlbaranVentaForm.jsx` son los dos pendientes más grandes por volumen de líneas.
7. `dias_caducidad_default` es nullable en ambas tablas de catálogo — el refactor debe decidir si sigue siendo opcional o pasa a NOT NULL con un valor por defecto.
